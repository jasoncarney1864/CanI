The 30‑second primer

AKS runs two layers. The control plane (API server, scheduler, etcd) is fully managed by Azure — you never see or patch it. The data plane is your nodes (VMs, grouped into node pools), which run pods (one or more containers). A deployment declares how many replicas of a pod you want running and rolls out changes; a service gives those pods a stable network identity; an ingress exposes a service to the internet with routing + TLS. Everything you'll triage during an incident is some flavor of "a pod isn't Running" or "traffic isn't reaching a pod."

3 Workloads — pods & deployments

This is the screen you'd reach for first in an outage. It's also where this cluster's biggest triage lesson lives.

Why the Portal can't show you pods here cani-aks33874b17's API server has no public endpoint (that's the point of a private cluster — smaller attack surface). The Portal's live Workloads/Pods/Services views talk to the API server directly from your browser, so unless your machine is on the cluster's VNet (VPN, bastion, or a jumpbox), those tabs will always show this error. Same reason Lens, k9s, or raw kubectl from your laptop won't connect either — they all need that same direct network path. This isn't a bug, it's the private-cluster design working as intended; your own CI/CD pipeline works around it with az aks command invoke, which tunnels through Azure's control plane instead of the VNet.

4 Services & ingress

How traffic actually reaches a pod, and where TLS certs live.

Conceptually: a Service is a stable internal DNS name + virtual IP in front of a changing set of pods (pods die and get replaced constantly — the Service doesn't). An Ingress sits in front of Services and does HTTP(S) routing + TLS termination for traffic coming from outside the cluster. On this cluster that's how app.canido.co reaches the web deployment, with cert-manager issuing and renewing the Let's Encrypt certificate automatically.

6 Mock triage: "app.canido.co is down"

Walking the same incident two ways makes the speed difference concrete. Here's the prompt-only path, using this cluster's real topology.

1

"Is anything actually broken, or is it DNS/network?"

Check pod status for the docs-platform namespace and any recent restarts in the last hour.
2

If pods look fine, check the edge

Check the ingress-nginx and cert-manager logs for errors in the last 30 minutes, and confirm app.canido.co's DNS still points at the right IP.
3

If a pod IS crash-looping, get the "why" in one shot

Pull the last 50 log lines and the most recent Kubernetes events for the crashing pod.
4

Rule out "it's not the app, it's the cluster"

Check node capacity and any recent AKS activity log events — deployments, scaling, restarts.
Where the line actually is today Everything above is diagnosis — reading pod status, logs, events, metrics, activity log — and all of it works through Azure Monitor / Resource Graph, so it's unaffected by the private-cluster restriction. Fixing it (restart a deployment, roll back, scale a pool) is a write action against the live API server, which still needs either VPN/bastion access, or running it through your existing az aks command invoke-based CI/CD path. I can talk you through the exact command to run, but I can't currently execute cluster writes myself in this setup — worth knowing before 2am hits.
