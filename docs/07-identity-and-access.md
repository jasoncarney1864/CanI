# 7. Identity & access (CanI Hub)

This section defines how CanI authenticates users once at the hub, authorizes access to spokes and documents, and enforces per-user isolation end to end.

## 7.1 Design principles

- Deny by default everywhere.
- One human identity per account, with least-privilege access to spokes and resources.
- Authorization decisions must be enforceable at multiple layers (hub, API, and data access), not only in UI routing.
- Keep external login simple for v1 while preserving a path to stronger controls (MFA policy, account recovery hardening, delegated admin).
- Treat identity metadata and audit trails as sensitive data because they reveal user behavior.

## 7.2 Authentication provider and protocol

**Decision:** Use Microsoft Entra External ID as the customer identity provider for end users.

Rationale:
- Native OpenID Connect and OAuth 2.1 patterns fit hub SSO and future mobile clients.
- Good alignment with Azure-hosted platform controls already selected in Sections 3 and 6.
- Centralized policy controls for sign-in risk, conditional access, and MFA rollout over time.

Protocol choices:
- Authorization Code + PKCE for browser and mobile clients.
- OIDC ID token for user identity at sign-in.
- Short-lived access tokens for API calls.
- Refresh token rotation enabled at the identity provider.

## 7.3 Identity and tenant model

CanI is logically multi-tenant at the data layer (many users isolated from each other), with a single product control plane in v1.

Identity objects:
- `user_id`: immutable internal UUID generated by CanI Hub and mapped to IdP subject (`sub`).
- `idp_subject`: stable identifier from Entra External ID.
- `status`: active, disabled, or pending-delete.
- `created_at`, `updated_at`, `last_login_at`.

Tenant and ownership model:
- In v1, each account is its own security boundary (single-user tenant model).
- Every document, chunk, conversation, and citation record carries `owner_user_id`.
- Future family/team sharing can introduce a `household_id` or `org_id` without breaking `owner_user_id` checks.

## 7.4 Authorization and entitlements

Authorization is policy-driven and evaluated server-side.

Core model:
- RBAC for coarse permissions (user, support-admin, platform-admin).
- ABAC/resource checks for ownership and scope (`owner_user_id == caller_user_id`).
- Spoke entitlements controlled by hub policy (`can_access_docs`, `can_access_legal`, `can_access_health`).

Policy rules:
- Hub routes only to spokes where entitlement is present.
- Spokes must re-check entitlement and ownership on every API call.
- CanI Docs retrieval path must enforce mandatory ownership filters before vector query execution.
- No anonymous or public document access path exists.

## 7.5 Session and token flow

1. User signs in at Hub through Entra External ID.
2. Hub creates an HttpOnly, Secure, SameSite session cookie for browser session continuity.
3. Hub mints short-lived internal access token for spoke/API calls with claims:
   - `sub` (mapped internal `user_id`)
   - `entitlements` (allowed spokes)
   - `auth_time`, `exp`, `jti`
4. Spoke validates token signature, expiry, and entitlement claims.
5. Data access layer enforces ownership filter regardless of token claims.

Token/session guidance:
- Access token lifetime target: 10-15 minutes.
- Session renewal with silent refresh and rotation, with replay detection on refresh token reuse.
- Force re-auth for high-risk actions (account recovery, data export, account deletion).

## 7.6 Service-to-service identity

Workload identities are separate from end-user identities.

- AKS workloads use Microsoft Entra Workload Identity, not static secrets.
- CanI Hub, CanI Docs, and background workers each get distinct managed identities and least-privilege RBAC.
- Internal service calls use mTLS-ready private networking assumptions from Section 6 and bearer token validation at each service boundary.

## 7.7 User lifecycle and access changes

Provisioning:
- First successful sign-in creates user profile and default entitlement set.
- Legal/Health spoke access can remain disabled until explicitly enabled.

Deprovisioning:
- Disable login immediately at IdP level.
- Mark internal user `disabled` and block token issuance.
- Queue asynchronous data retention/deletion workflow per policy.

Entitlement change behavior:
- Changes are effective immediately for new requests.
- Existing sessions are revoked on critical entitlement removals.

## 7.8 Audit and monitoring requirements

Must log at minimum:
- Authentication success/failure and lockout events.
- Entitlement grant/revoke events with actor and timestamp.
- Authorization denials at spoke APIs.
- Administrative actions affecting user access.

Telemetry requirements:
- Correlate identity events with request traces via shared correlation ID.
- Send identity audit logs to centralized Log Analytics workspace.
- Alert on suspicious access patterns (repeated denials, unusual location shifts, token replay indicators).

## 7.9 v1 implementation checklist

- Entra External ID tenant/app registration configured for Hub OIDC.
- Hub session middleware with secure cookie settings and CSRF protection.
- Entitlement store and policy middleware in Hub API.
- Spoke-level authz middleware enforcing entitlement + ownership checks.
- Mandatory owner filter integrated into CanI Docs retrieval/query path.
- Audit events emitted for all authn/authz state transitions.

## 7.10 Open questions

2. What is the exact support-admin model for a solo developer without broad read access to user document content?
3. What retention period applies to identity and audit logs versus document data deletion timelines?
